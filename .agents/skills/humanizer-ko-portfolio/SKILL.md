# 한국어 포트폴리오 문구 편집

현재 사용자 요청과 작성자의 말투를 기준으로 읽기 쉬운 한국어 경력 문구를 만든다. AI 작성 여부를 판정하거나 탐지기 점수·통과를 약속하지 않는다.

## 원본 Humanizer 활용

일반 문체 패턴을 검토할 때 [원본 Humanizer](../humanizer/SKILL.md)를 함께 읽는다. 원본의 과장·반복·장식적 강조·불필요한 대비 검토를 사용하되 한국어 문법과 이 프로젝트의 사실 보존 기준에 맞춰 적용한다. 원본 파일 모드의 데이터 보호 원칙은 아래의 코드 내 공개 문구 편집 범위로 구체화한다. 숫자·기간·기술명과 의미 있는 제약은 문장 리듬을 위해 삭제하지 않는다.

## 한국어 편집 기준

- `~고,`, `~며,` 뒤 쉼표는 문장 이해에 필요한지 판단한다. 긴 문장은 의미 단위로 나누고 나열에 필요한 쉼표는 남긴다.
- 어려운 한자어와 추상어는 실제 작업으로 풀어 쓴다. `역량을 확보했다`, `범위를 확장했다`, `구체화했다`를 반복하기보다 무엇을 정하고 구현했는지 적는다.
- 단문과 복문을 의미에 맞게 섞는다. 같은 종결어나 기술명이 반복된다는 이유만으로 부정확한 동의어로 바꾸지 않는다.
- 경험에서 근거 없는 성과·가치·인과관계로 비약하지 않는다. 운영 규모를 개선율로, 참여를 전담으로, 검증을 운영 성과로 바꾸지 않는다.
- 작성자가 제공하지 않은 감정·취향·일화·평가를 추가하지 않는다. 친근한 말투, 수사적 질문, 농담을 강제로 넣지 않는다.
- 기술 분류·프로젝트 제목·날짜 범위의 가운데점과 대시, 목록·불릿은 의미가 있으면 유지한다. 영어 문체 규칙을 한국어에 기계적으로 적용하지 않는다.
- 이미 자연스러운 문구는 그대로 둔다. 기존 화면의 항목 구성과 문구 길이를 고려해 필요한 부분만 고친다.

## 이 프로젝트의 합의된 방향

최신 사용자 요청이 다음 기본값을 바꾸면 그 요청을 따른다.

- 소개는 현재 맡는 업무, 구현한 기능, 설계 이유와 운영 문제 해결을 중심으로 쓴다. `프론트엔드에서 시작해 백엔드로 확장` 같은 성장 서사를 반복하지 않는다. Frontend 기술 분류와 프로젝트의 실제 화면 개발 역할은 정확하게 유지한다.
- 랜딩페이지의 사설 교육 수강 항목은 삭제된 상태를 유지한다. 이력서에는 `IT 스칼라 · AI Agent 교육 수강` 한 줄을 남긴다. 교육을 경력 성과나 자격으로 확대하지 않는다.
- KBO Mate는 개발 중인 개인 프로젝트로 설명하고 상용 운영 경험과 구분한다.
- 담당 범위와 검증 한계는 자연스러운 문장으로 설명하되 정확성에 필요한 내용은 남긴다.

## 사실 확인과 편집 대상

현재 소스와 최신 사용자 정정을 기준으로 삼는다. 다음 파일은 요청한 페이지에 해당할 때만 읽는다.

- 이력서: `src/data/resume.ts`, `src/app/resume/ResumePage.tsx`, `src/app/resume/page.tsx`.
- 랜딩: `src/components/domain/home/ReferenceHome.tsx`, `src/components/domain/home/Section3/index.tsx`, 사용 중인 `src/data/careerData.ts` 필드.
- 프로젝트: `src/data/projects.ts`, `src/data/projectCaseStudies.ts`, `src/data/work.ts`, 해당 화면 컴포넌트. 공유 데이터와 상세 override를 함께 확인한다.
- 검색·공유 설명: 요청된 범위에서 페이지 metadata와 `src/lib/seo/config.ts`의 description만 검토한다.

상담 건수와 집계 기간, 합성 데이터 테스트와 실제 알림 수신 여부, 배포 소요 환경과 절감 성과, 기존 서버·인프라 사용과 신규 구축, 관리자 영역과 사용자 화면, 출시 보류와 운영 중 상태를 구분한다. 참고용 과거 문서와 `public/resume.txt`의 포괄적 주장을 최신 공개 소스보다 우선하지 않는다. 근거가 부족하면 기존의 정확한 범위를 유지하거나 확인이 필요한 사실을 짧게 표시한다.

## 요청별 작업 범위

- 검토·수정안 요청: 파일은 변경하지 않고 필요한 원문과 권장안, 수정 이유를 제시한다.
- 반영 요청: 승인된 범위의 문구를 파일에 적용한다. 세부 표현을 고칠 때마다 재승인을 요구하지 않는다.
- 일반 산문은 문맥에 맞게 편집한다. TS·TSX·구조화 데이터에서는 공개 설명용 문자열과 JSX 텍스트만 변경한다. 문자열 전체가 편집 대상이라고 가정하지 않는다.
- 객체 키, ID·slug, 날짜·수치 값, 기술 스택, URL·링크 대상, CSS 클래스, 함수·타입·코드 구조, 설정·동작은 보존한다. JSX 내부 공백과 문자열 이스케이프가 렌더링에 미치는 영향도 확인한다.
- 관련 없는 페이지, 미사용 레거시 데이터, 블로그 원문이나 제출 원본까지 확장하지 않는다. 커밋·push·배포는 해당 요청이 있을 때만 진행한다.

## 확인과 전달

편집 전후를 대조해 사실 누락·과장·담당 범위 변화와 코드 손상이 없는지 확인한다. 코드 내 문구를 수정했다면 diff 검사와 변경 파일 lint·타입 검사 등 변경 규모에 맞는 검증을 수행한다. 제목이나 긴 문장 변경으로 줄바꿈이 우려되면 해당 페이지의 모바일·데스크톱 표시를 확인한다. 기존 검사 실패는 새 실패와 구분해 보고한다.

결과는 사용자 요청에 맞춘 최종 문구 또는 적용 내용과 검증 결과로 간단히 전달한다. 내부 초안과 자기평가를 모두 출력할 필요는 없다.
